## Security Risks

### NEW — `joserfc` 1.6.5 (pinned) affected by CVE-2026-49852 — empty/nil HMAC key accepted as valid signature
**GHSA-gg9x-qcx2-xmrh, CVSS 7.5 HIGH.** `joserfc.jwt.decode` accepts HS256/HS384/HS512-signed tokens when the verification key is the empty string or `None` — `OctKey.import_key` only warns (doesn't reject) zero-length keys. Cross-language sibling of `ruby-jwt`'s CVE-2026-45363. Fixed in **1.6.8** ("Reject empty OctKey"). The repo pins **1.6.5** (`backend/requirements.txt`), inside the vulnerable range.
**Repo-specific exposure check:** `backend/app/core/config.py:9` defaults `jwt_secret_key` to the non-empty string `"dev-secret-change-in-production"`, and `backend/app/core/security.py` uses this setting for both encode and decode. The zero-length-key forgery path requires the *actual configured secret* to be empty/`None` at runtime — not the case with the current default. Risk is contingent on an ops/deployment mistake (e.g., an unset `JWT_SECRET_KEY` env var resolving to `""` in some environment), not a default-config exposure.
**Action:** bump `joserfc==1.6.5` → `>=1.6.8` in `backend/requirements.txt`. One line, no behavior change for correctly-configured deployments. Given CLAUDE.md's own security checklist item ("validate that required secrets are present at startup"), also worth confirming `Settings` raises/fails fast if `JWT_SECRET_KEY` is explicitly set to an empty string in production, rather than silently falling through to a default or empty value.

### OPEN (5th cycle) — Starlette version floor below CVE-2026-48710 fix
`backend/requirements.txt` still pins `starlette>=0.49.1`, unbounded. CVE-2026-48710 ("BadHost", Host-header auth bypass, GHSA-86qp-5c8j-p5mr) affects Starlette <1.0.1, fixed at 1.3.1. ## Implementation References

### #509 — Block Catalogue dispatch-table refactor
**New reference found.** No packaged if/elif-to-dispatch-table codemod exists for Python or TS (re-confirmed, ast-grep/Codemod registries still empty on this). But **ComfyUI's V3 node system is a concrete architectural precedent**: each node defines a single `define_schema()` (an `io.Schema`) that is the one source of truth consumed by both the execution engine (binds params by the schema's declared IDs) and the UI/registry layer — explicitly designed to replace an earlier "opaque dict" approach that caused execution/UI drift (docs.comfy.org/registry/overview). This maps directly onto #509's goal: define each block type's schema/dispatch entry once in the shared Block Catalogue, and have `interpreter.py` (already catalogue-driven), `explanation.py`, and `explanation-generator.ts` all consume the same source rather than maintaining three independent forks. No tool to adopt — a pattern to emulate manually, same as prior cycles' conclusion, but now with a named reference implementation worth reading before writing the spec.

### #510 — Pydantic → Zod codegen seam
**New negative finding — the previously-recommended fork is stale.** `@dmitryrechkin/json-schema-to-zod`, recommended last cycle as the maintained alternative to the unmaintained `json-schema-to-zod`, has had no commit since **2025-03-10** (still at v1.0.1) and is **incompatible with Zod v4** (Zod v4 removed/renamed `ZodSchema` to `ZodType`; confirmed via inngest/inngest#3764 hitting the same incompatibility). If the frontend's Zod dependency is v4, this fork is not viable as-is. `pydantic2zod` remains stagnant. No new maintained entrant found, and no Pydantic-core-team movement toward official TS/Zod codegen. **Revised recommendation:** treat this as "no viable off-the-shelf tool" rather than "use the maintained fork" — the realistic near-term path is Pydantic's built-in `model_json_schema()` as an intermediate representation feeding a small hand-written TS generator, since the cross-field rules that actually matter here (take-profit ladder ascending order, ≤100% total) won't survive *any* of these generators unmodified and need hand-written refinements on both sides regardless of tool choice.

### #511 — Atomic `submit()` / commit-then-enqueue seam
**New, concrete, portable pattern found.** SQLAlchemy maintainer guidance (sqlalchemy/sqlalchemy#9116): register a `session.after_commit` event listener; inside it, do **not** reuse the original session (attempting SQL there raises `InvalidRequestError`) — instead open a separate short-lived Session/connection to perform the enqueue. Since SQLModel sits directly on SQLAlchemy, this is a direct, non-Django equivalent of django-rq's `on_db_commit` mode (previously the only reference found): commit the `backtest_run` row → `after_commit` fires → listener opens a fresh session, calls `rq.enqueue()`, marks the row `enqueued` on success; on failure the row stays `pending`/retryable. This closes the gap the last three cycles flagged (no non-Django RQ-native recipe existed). Noted only as a longer-term alternative, out of scope for #511 as spec'd: Postgres-native transactional-enqueue tools (`raquel`, `ricwo/pq`) would mean replacing Redis/RQ entirely.
