A grep of `frontend/src` found no `next/image` use. Earlier greps found no `use cache` and no `"use server"`. None of the three advisories appears to apply directly, but the official post says to upgrade regardless.
3. **`sharp` is resolved at `0.34.5` in the lockfile** (below the `0.35.5` workaround). That matters only if the image runtime moves to glibc or `next/image` is adopted. Upgrading Next.js pulls in a fixed `sharp`.
4. **Redis server: possible in-the-wild exploitation.** The Canadian Cyber Centre updated AV26-423 on 2026-10-19: open-source reports say CVE-2026-25243 is being exploited. The Redis server image version used in compose was not checked this cycle; do so.
5. **Separate hygiene item:** `node:20` reached end of life in April 2026 (from general knowledge, not checked this cycle). Worth a plan to move the frontend image to a supported Node LTS.
6. **No open issue is blocked by upstream changes.** #618, #570, #555 still wait on the human PostHog tasks #620, #573, #561.

## Security Risks

### P0 — Next.js `16.2.6` behind the 2026-10-14 update
Sources: [Next.js security update, October 14 2026 (official)](https://nextjs.org/blog/nextjs-security-update-october-14-2026), [Singapore CSA AL-2026-148](https://www.csa.gov.sg/alerts-and-advisories/alerts/al-2026-148/).

| Advisory | Severity | Condition | Repo status |
|---|---|---|---|
| GHSA-673q-mjm6-r5xr | Critical | App Router + Cache Components, `use cache` returning multiple typed arrays; no workaround | no `use cache` found |
| CVE-2026-96889 / GHSA-2464-fhr4-w9xw | Critical | Image Optimization API (SVG), glibc Linux; workaround `sharp` >= 0.35.5 | Alpine (musl), no `next/image` use found; lockfile `sharp` 0.34.5 |
| GHSA-p3m5-59mp-jv5r | High | App Router with at least one Server Action; CPU DoS | no `"use server"` found |

- The post says to upgrade immediately even without matching code. `npm install next@16.4.1`.
- Recommendation: human-approved bump to `next@16.4.1` (or a newer 16.x patch) with `react`/`react-dom` aligned. It crosses 16.2 to 16.4, so run `cd frontend && npm test && npm run lint && npm run build` and read the 16.3/16.4 release notes first. Not done here (no source edits in this task).
- Caveat: my greps cover `frontend/src` and `next.config.*`. Third-party packages could still use these paths; the advisory conditions are about the app's own code, so low likelihood.

### P1 — Redis server (CVE-2026-25243 reportedly exploited)
Sources: [Cyber Centre AV26-423](https://cyber.gc.ca/en/alerts-advisories/redis-security-advisory-av26-423), [Cyber Centre AV26-859](https://cyber.gc.ca/en/alerts-advisories/redis-security-advisory-av26-859), [Redis advisory (CVE-2026-23479, -25243, -25588, -25589, -23631)](https://redis.io/en/blog/security-advisory-cve202623479-cve202625243-cve-2026-25588-cve202625589-cve-2026-23631/).
- Authenticated-user RCE class. Redis backs OAuth state, password-reset rate limits and RQ, so compromise would be serious.
- Action: confirm the Redis image tag in `docker-compose*.yml` and compare with the fixed versions in the advisory. Ensure Redis is not published on a public interface and requires a password. I did not verify fixed version numbers (the search snippets did not list them).

### P1 — Starlette (carried)
Sources: [Debian DSA-6302-1](https://lists.debian.org/debian-security-announce/2026/msg00213.html), [Fedora backport](https://linuxsecurity.com/advisories/fedora/fedora-44-python-starlette-2026-3bce8d3f11).
- CVE-2026-48710: Host header not validated before building `request.url`, enabling a bypass of checks that rely on it. The `>=0.49.1` floor does not guarantee a fixed install. Run `pip show starlette` in the backend image; check whether any code uses `request.url` for redirects, OAuth callbacks or reset links. Auth-adjacent, so human approval is needed for pin changes.
