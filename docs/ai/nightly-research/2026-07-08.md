## Security Risks

### OPEN (4th cycle) — Starlette version floor below CVE-2026-48710 fix
`backend/requirements.txt` still pins `starlette>=0.49.1`, unbounded, no lockfile. CVE-2026-48710 ("BadHost", Host-header auth bypass, GHSA-86qp-5c8j-p5mr) affects all Starlette <1.0.1; fixed version remains 1.3.1. FastAPI's own floor (`fastapi==0.139.0` → `requires_dist: starlette>=0.46.0`) still hasn't moved, and the maintainer discussions declining to narrow it (#15193, #15593) show no new activity. Not currently exploitable in a fresh build (pip resolves to 1.3.1 today), but the gap is a silent regression risk on any stale cached layer or future FastAPI downgrade.
**Action:** change `starlette>=0.49.1` to `starlette>=1.0.1` (or `>=1.3.1` to track current) in `backend/requirements.txt`. One line, no behavior change. Four consecutive cycles recommending this without it being applied — see Questions.

### NEW — React 19.2.6 (repo's pinned version) has a known Server Actions/FormData regression, fixed in 19.2.7
React/React-DOM 19.2.7 (released 2026-06-01) fixes a regression in FormData handling within Server Actions that was introduced in 19.2.6 — the exact version this repo has pinned (`frontend/package.json`). This is a correctness/reliability issue rather than a security CVE, but is directly actionable: any form submitted through a Server Action on this app could be hitting the bug today. No new information changes this since 19.2.7's original release; it was not flagged in the 2026-07-06 report and is being surfaced now.
**Action:** bump `react`/`react-dom` to `19.2.7` (or later) and verify any Server Action forms (e.g., auth, strategy save, profile settings) still submit correctly.

### RESOLVED / CONFIRMED SAFE — Redis and PostgreSQL server CVEs
`redis:7.4.9-alpine` (Docker) remains the fixed release for CVE-2026-23479/23631 and the related batch — no new Redis server CVEs since 2026-06-30. `postgres:16-alpine` (Docker, floating tag) continues to resolve to a patched 16.14+ build covering CVE-2026-2005 (pgcrypto heap overflow) — no new PostgreSQL CVEs since 2026-07-06. Both are unchanged from last cycle; the same reproducibility caveat stands (stale cached image layers from before the respective patch dates would still be vulnerable).

### STANDING GUARDRAIL — redis-py 8.x / RQ version coupling
redis-py remains at 8.0.1 (RESP3-by-default breaking change). RQ 2.9.1 (~2026-06-06) is confirmed as the release that added redis-py 8.x compatibility; RQ has since moved to 2.10.0. The repo's pins (`redis==7.1.1`, `rq==2.7.0`) remain mutually compatible today and are unaffected. Unchanged from last cycle: **do not bump `redis` past 7.x without bumping `rq` to >=2.9.1 in the same change.**

### NEW (informational) — uvicorn 0.51.0 released today, non-security
Ships SIGHUP-triggered overlapping worker restarts (near-zero-downtime reloads) and drops `colorama` from the `standard` extra. Repo pin (`0.47.0`) is three minors behind. No CVE, no urgency, but a reasonable candidate for the next routine dependency-refresh pass.

## UX Research

Two genuinely new, dated items surfaced this cycle (prior cycles' items — ComfyUI Nodes 2.0, Composer.trade's merged NL/Discover surface, TrendSpider Sidekick — are not repeated here as they're unchanged):

- **n8n "Canvas Groups"** (announced 2026-07-06, shipping v2.28.3+): lets users drag-box or Ctrl/Cmd+click a connected run of nodes and collapse them into a single named, persisted block. This is a *group-and-collapse* abstraction, distinct from this project's per-node **Compact Node Display Mode** (§4.12 of product.md, which compacts each node individually rather than grouping several into one). Worth a look as a complementary pattern for large strategies with many blocks, not a replacement for the existing compact mode.
  Source: https://community.n8n.io/t/announcing-canvas-groups-expand-and-collapse-node-groups/302304
- **n8n v2.30.0 `validate_node_config` tool** (released 2026-07-07): exposes per-node config validation as a callable tool for AI agents building workflows, checking a node in isolation before it's wired into the full graph. It's agent-facing rather than a human-visible UI, but it's a second data point (alongside TrendSpider's Sidekick loop, noted previously) that "validate before/at the node level, not just at submit time" is a recurring pattern — directionally consistent with this project's existing **Visual Strategy Validation Feedback** (§4.9) and **Health Bar** (§4.17) work, which already validate inline per-block rather than only at submission.
  Source: https://releasebot.io/updates/n8n (aggregator; primary changelog at https://docs.n8n.io/changelog not independently re-confirmed)

No new dated material found on wizard-vs-natural-language onboarding patterns, or on strategy/workflow "completeness" indicators outside generic B2B customer-health-score content (not applicable to canvas UX).
