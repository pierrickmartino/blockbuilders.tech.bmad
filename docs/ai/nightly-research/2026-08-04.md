## Security Risks

### P1, NEW TODAY — npm supply-chain worm ("ChainDrop"): `keyv`/`cacheable`/`flat-cache`/`file-entry-cache` family compromised; repo's resolved versions are unaffected, but treat as an active-incident caution
On 2026-08-04, an attacker took over the GitHub account of the maintainer behind `keyv` and the broader `cacheable` caching-library family and published trojanized releases carrying a malicious `preinstall` hook (`setup.mjs`) that downloads a Bun runtime, harvests CI/cloud credentials, and self-propagates using any npm publish tokens it finds. Confirmed-compromised versions include `keyv@6.0.0`, `flat-cache@6.1.24`, `file-entry-cache@11.1.6`, `cacheable@6.0.0`, `@cacheable/utils@2.5.1`, `cacheable-request@13.0.20`, `cache-manager@7.2.10`. Reports (Wiz, Aikido, StepSecurity, BleepingComputer) put the scope between ~400 and 1,300+ packages / 2,000+ versions within about four hours, spanning 2B+ combined monthly downloads. The malware additionally plants persistence via a Claude Code startup hook and a VS Code task, so simply opening an infected repo in those tools can re-trigger it without a fresh install.
**Repo-specific check (done directly against `frontend/package-lock.json`, not assumed):** this repo resolves `keyv@4.5.4`, `flat-cache@3.2.0` (via `@storybook/react-docgen-typescript-plugin`) and `flat-cache@4.0.1`, and `file-entry-cache@8.0.0` — all pre-existing major versions well below the compromised releases, pulled in transitively by ESLint/Storybook dev tooling, not runtime code. None of `cacheable`, `cacheable-request`, `cache-manager`, or `@cacheable/utils` appear anywhere in the lockfile. `frontend/.github/workflows/ci.yml` runs `npm ci` (line 37), which installs exactly the lockfile's resolved versions and does not consult semver ranges against the registry — so CI will not silently pull a poisoned version.
**Action:** no immediate code change needed. Caution items: (1) do **not** run `npm update`, `npm install <pkg>@latest`, or regenerate `package-lock.json` from scratch for anything touching ESLint/Storybook tooling until the ecosystem confirms `keyv`/`cacheable`-family packages are clean again (safe restored versions reported so far: `keyv@5.6.0`, `flat-cache@6.1.23`, `cache-manager@7.2.9`); (2) if any contributor opened this repo in Claude Code or VS Code today from an *unrelated* infected project on the same machine, that machine's credentials should be treated as potentially compromised per the persistence mechanism described above — this is a host-level concern, not a repo-level one, but worth a heads-up to the team.
