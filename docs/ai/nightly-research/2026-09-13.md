## Security Risks

### P0 → RE-ASSESSED, NOT DOWNGRADED — Starlette "BadHost" (CVE-2026-48710): fresh installs of this repo's pins already resolve past the fix floor, but the KEV deadline (2026-09-16) is now 3 days out
This is the same advisory tracked for 8+ cycles (GHSA-86qp-5c8j-p5mr, CVSS 6.5, Host-header path-reconstruction auth bypass, affects Starlette 0.8.3–1.0.0, fixed in 1.0.1), added to CISA's Known Exploited Vulnerabilities catalog on 2026-09-02 with **federal remediation due 2026-09-16**.
**New this cycle:** ran `pip install --dry-run -r backend/requirements.txt` against the actual committed file (not just `fastapi==0.136.1` in isolation). Result: **Starlette resolves to 1.6.0** — confirmed via the dependency-resolver's own version selection (`fastapi`'s own constraint is `starlette>=0.46.0`; the repo's tighter `starlette>=0.49.1` line doesn't change the outcome since neither bounds the ceiling). 1.6.0 is well past the 1.0.1 fix floor.
**What this does and doesn't tell us:** it proves a *clean* install today is not exposed. It does **not** prove the actual running dev/CI/prod environment is on 1.6.0 — Docker layer caching keyed on an unchanged `requirements.txt` hash will keep serving whatever Starlette wheel was resolved at the image's last cache-busting rebuild, which could predate 1.6.0. It also doesn't protect against a future regression: an unbounded floor means the next `pip install` after a hypothetical Starlette security regression would adopt it silently.
**Action (unchanged, still recommended, urgency softened but not removed):** pin `starlette>=1.0.1` explicitly in `backend/requirements.txt` — closes the KEV-listed bypass by contract rather than by incidental resolver behavior, and removes the ambiguity this report has carried for 8 cycles. Given the 2026-09-16 deadline is now 3 days away, also worth an operator directly confirming the *deployed* environment's resolved version (`pip show starlette` in the running container) rather than relying on a fresh dry-run.
