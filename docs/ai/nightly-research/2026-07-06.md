## Security Risks

### OPEN (3rd cycle) — Starlette version floor below CVE-2026-48710 fix
`backend/requirements.txt` still pins `starlette>=0.49.1`, unbounded, no lockfile. CVE-2026-48710 ("BadHost", Host-header auth bypass, GHSA-86qp-5c8j-p5mr) affects all Starlette <1.0.1; fixed version is now 1.3.1 (2026-06-12). **New this cycle:** FastAPI maintainers have explicitly declined, in two separate discussions (#15193, #15593), to narrow FastAPI's own Starlette floor — this confirms the fix has to happen at the application level (this repo), not upstream. Not currently exploitable in a fresh build (pip resolves to 1.3.1 today), but the gap is a silent regression risk on any stale cached layer or future FastAPI downgrade.
**Action:** change `starlette>=0.49.1` to `starlette>=1.0.1` (or `>=1.3.1` to track current) in `backend/requirements.txt`. One line, no behavior change. This has now been recommended for three consecutive cycles without being applied — treat as ready to merge, not just "approve."

### RESOLVED / CONFIRMED SAFE — Redis server CVEs
`redis:7.4.9-alpine` (Docker) remains the fixed release for CVE-2026-23479, CVE-2026-23631, and the related 2026-05 disclosure batch. No new Redis server CVEs found since 2026-06-30. (Reminder from last cycle still stands: `redis==7.1.1` in `backend/requirements.txt` is the **client library**, a separate artifact from the Docker server image — do not conflate the two version numbers.)

### NEW — CVE-2026-2005 (PostgreSQL pgcrypto heap overflow, high severity)
Fixed in the same May 2026 cumulative batch as 16.14/17.10/18.2/18.4. The repo's `postgres:16-alpine` Docker tag is floating (not digest-pinned), so it already resolves to a patched 16.x build on any fresh pull — **no action needed**, but flagged as the same reproducibility class of risk as the Starlette floor: a stale cached image layer from before 2026-05-14 would still be vulnerable. Consider whether CI/deploy image builds are pulling fresh often enough to rely on this, or whether an explicit minimum patch version should be documented.

### NEW — redis-py 8.0.1 / RQ version coupling guardrail
redis-py 8.0.1 (2026-06-23) defaults to the RESP3 wire protocol — a breaking change for older RQ versions. RQ only added redis-py-8 compatibility in 2.9.1. The repo's current pins (`redis==7.1.1`, `rq==2.7.0`) are mutually compatible today, so this is not an active issue, but it's a new dependency-bump trap: **bumping `redis` to 8.x requires bumping `rq` to >=2.9.1 in the same change**, or job processing will break. Worth a one-line comment in `requirements.txt` or a note in the upgrade runbook so a future isolated dependency bump doesn't trip over it.

### MONITOR — No other new CVEs this cycle
FastAPI, SQLModel, Alembic, psycopg2-binary, rq-scheduler, Next.js, React, TypeScript, Tailwind CSS, @xyflow/react: no new security advisories found since 2026-06-30 against any current or latest-available version.

### #510 — Pydantic → Zod codegen seam
`pydantic2zod` looks increasingly stagnant — no real PRs since May 2025, no release since Nov 2024, and its PR history shows no discussion of custom/cross-field validators (the identified gap: the take-profit-ladder ascending-order check and the ≤100%-total check). `json-schema-to-zod` (the JSON-Schema-intermediary candidate) is now flagged unmaintained by its own maintainers; **`@dmitryrechkin/json-schema-to-zod`** is the actively-maintained fork and should replace it as the candidate if that path is chosen. One new tool surfaced — **`dhi`** (github.com/justrach/dhi, v1.5.0, 2026-06-12) — a Zig-core validator exposing Pydantic-compatible Python and "Zod 4"-compatible TS APIs from one core; however it requires writing the schema in each language separately (not single-source codegen) and its docs don't cover custom cross-field validators either, so it's a footnote/future option, not a solution to the identified gap.

### #511 — Atomic `submit()` / commit-then-enqueue seam
**Nothing new.** No RQ-specific (as opposed to django-rq) commit-then-enqueue recipe was found. Alternative Postgres-native queue implementations (`malthe/pq`, `py-q4pg`) and DBOS's general transactional-outbox docs surfaced but aren't recipes for the actual raw-RQ + SQLModel stack in use. Last cycle's recommendation stands unchanged: replicate django-rq v3.0's "enqueue only after DB commit" semantic manually (commit the run row via an on-commit hook, enqueue after, leave a retryable row if enqueue throws).
