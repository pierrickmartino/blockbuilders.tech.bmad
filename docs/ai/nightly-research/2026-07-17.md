## Security Risks

### NEW — Next.js formal security-release program; first scheduled patch targets 2026-07-20, covers this repo's exact 16.2.x line
Vercel published ["Next.js Security Release and Our Next Patch Release"](https://nextjs.org/blog/next-security-release-program) on **2026-07-13**, announcing a monthly, pre-announced security-release cadence (replacing ad-hoc patches). **The first scheduled release targets publication on 2026-07-20** — three days after this report — and will patch **Next.js 16.2 and 15.5**, fixing **4 high-severity and 5 medium-severity** vulnerabilities. No CVE IDs or technical details are public yet; Vercel says it will publish specifics once the patch ships. Separately, prior known advisories (GHSA-8h8q-6873-q5fj DoS-via-Server-Components, GHSA-267c-6grr-h53f/GHSA-26hh-7cqf-hhc6 middleware/proxy segment-prefetch bypass) are already fixed as of 16.2.6/15.5.18 — this repo's pinned 16.2.6 already includes those fixes, they are not new exposure.
**Action:** no fix exists yet — nothing to apply today. Flag for the 07-20 release: check `frontend/package.json`'s `next` pin against the patched version as soon as it publishes, and treat it as P1 given the announced severity mix and that it targets this repo's exact minor line.

### OPEN, unchanged — Starlette version floor below CVE-2026-48710 ("BadHost") fix
`backend/requirements.txt` still pins `starlette>=0.49.1`, unbounded, no lockfile. Fixed version remains 1.3.1 (1.0.1 is the minimum patched release, shipped 2026-05-21). No new developments on the CVE this cycle — all sources retrieved (badhost.org, CCB Belgium advisory, Hacker News, the FastAPI discussion thread) predate 2026-07-08. As established in a prior cycle, this repo's own code was checked and is **not** exposed to the secondary `request.url.path`-based risk class (only two usages, both in non-security logging middleware in `app/main.py`; OAuth `redirect_uri` is built from configured `settings.frontend_url`, never request Host data) — the outstanding fix genuinely is the one-line dependency floor bump.
**Action:** change `starlette>=0.49.1` to `starlette>=1.0.1` (or `>=1.3.1` to track current) in `backend/requirements.txt`.

### STANDING — React 19.2.6 (repo's pinned version) has a known Server Actions/FormData regression, fixed in 19.2.7
Unchanged: React/React-DOM 19.2.7 (released 2026-06-01) fixed a FormData-handling regression in Server Actions introduced in 19.2.6, the exact version this repo has pinned. Not a CVE, but directly actionable — any form submitted through a Server Action (auth, strategy save, profile settings) could be hitting this.

### CONFIRMED SAFE — Redis and PostgreSQL server images; PostgreSQL CVE batch is old news
The May 2026 PostgreSQL CVE batch (CVE-2026-6472 through -6479, -6575, -6637, -6638 — 11 CVEs total, released 2026-05-14) resurfaced in this cycle's search results but is the **same** batch already covered and resolved in prior reports; `postgres:16-alpine` (floating tag) continues to resolve to a patched 16.14+ build. `redis:7.4.9-alpine` remains the fixed release for the prior CVE batch. No new PostgreSQL or Redis server CVEs since 2026-07-08.

### GUARDRAIL, refined — redis-py 8.x / RQ version coupling
Refinement from prior cycles: redis-py 8.0+ now uses RESP3 on the wire **by default**, but — contrary to the blanket "breaking change" framing in earlier reports — it **keeps legacy RESP2-compatible Python response shapes by default** (`legacy_responses` defaults to preserving old shapes; set `protocol=2` to force RESP2 on the wire, or `legacy_responses=False` to opt into the new unified shapes). RQ has since added formal compatibility with redis-py >=8. Repo's current pins (`redis==7.1.1`, `rq==2.7.0`) are unaffected today. Guardrail unchanged: **do not bump `redis` past 7.x without bumping `rq` to >=2.9.1 in the same change**, and note the response-shape migration is less disruptive than previously described if/when that bump happens.

### MONITOR — No other new CVEs this cycle
FastAPI (0.139.1/0.139.2, 2026-07-16 — dotted-path routing fix and a test-parallelism thread-safety refactor, neither security-relevant), SQLModel, Alembic, psycopg2-binary, RQ, rq-scheduler, Tailwind CSS, uvicorn, @xyflow/react, httpx, boto3, stripe: no new security advisories found since 2026-07-08 against any current or latest-available version.

## UX Research

**New and directly relevant to #618 (NL-wedge onboarding A/B, currently blocked on #620):** FlowTrade's Strategy Builder ships an "AI Strategy Agent" that takes a plain-English description of a trading idea and places nodes, sets parameters, and wires connections onto the same visual canvas for the user to review and refine — i.e., natural-language input that lands as an editable, inspectable node graph rather than a black-box result. This is the closest found-in-the-wild precedent for exactly the wizard-vs-NL-box tradeoff #618 is designed to A/B test, and reinforces the "transparency" pattern already noted in general no-code/AI-copilot research this cycle: pairing NL input with a visible, verifiable canvas so the user can confirm what was actually built before trusting it. Composer (by SoFi) has a similar but less mature NL-to-strategy feature that "requires manual refinement for production use" — worth noting as the weaker version of the same pattern. Neither is new architecture guidance (this project's canvas/validation/health-bar primitives already support "inspect and correct" once #618 unblocks), but both are concrete, dated evidence that the NL-wedge approach under test in #618 has real-world precedent worth citing if/when that PRD needs supporting examples.

No other genuinely new, dated pattern surfaced this cycle beyond what prior reports already logged (n8n Canvas Groups, ComfyUI Nodes 2.0, TrendSpider Sidekick — all previously cited, not repeated here).
