### #510 — Pydantic → Zod codegen seam
This cycle's search reinforced rather than changed the standing recommendation: 2026 writeups now consistently frame **JSON Schema as the language-agnostic bridge** (`Model.model_json_schema()` on the Python side → converted to Zod on the TS side) as the dominant pattern, over any direct Pydantic→Zod codegen tool. `pydantic2zod` remains the only named direct-conversion tool and is still not materially more mature. No tool auto-generates the cross-field validators (take-profit-ladder ascending-order + ≤100%-total checks) from one source of truth — every surveyed 2026 approach still hand-writes `.refine()`/`@field_validator` pairs on each side. Recommendation unchanged.

### #511 — Atomic `submit()` / commit-then-enqueue seam
Reinforced, not changed: 2026 material (including a dated Redis-authored writeup on Redis Streams as an outbox transport) continues to converge on the **transactional outbox pattern** — write the job row in the same DB transaction, relay to the queue afterward, leave a retryable row if the enqueue throws — with at-least-once delivery and idempotent consumers as the accepted trade-off. No RQ-native (non-Django) commit-then-enqueue package exists; `django-rq`'s `COMMIT_MODE='on_db_commit'` remains the closest packaged reference. Recommendation unchanged: replicate the outbox semantic manually against SQLModel + RQ.
