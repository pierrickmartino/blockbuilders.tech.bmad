## Security Risks

### P1, NEW THIS CYCLE — Redis server: `redis:7.4.9-alpine` (repo's exact pinned tag) has an unpatched authenticated-RCE-class bug; fix is `7.4.10`
Disclosed 2026-07-23 (surfaced via AI-agent security research, reported by The Hacker News 2026-07-24; independently corroborated via `howtofix.guide` and ZeroDay.cloud):
- **Bug class 1:** Streams `RESTORE`-payload shared-NACK use-after-free — a corrupted RDB stream object can make two consumers reference the same pending-entry record; removing both frees the same object twice.
- **Bug class 2:** RedisBloom/TDigest out-of-bounds write, also reachable via `RESTORE`.
- **PoC status:** authenticated RCE PoCs published against stock Redis 6.2.22, **7.4.9**, 8.6.4, and 8.8.0 — i.e., the very versions the May 2026 security round told users to install did *not* include the shared-NACK ownership guard.
- **Fix versions:** 6.2.23, 7.2.15, **7.4.10**, 8.2.8, 8.4.5, 8.6.5, 8.8.1 (branch-specific; repo needs `7.4.10`).
- **CVE status:** no CVE/CVSS assigned as of today — Redis's own July release notes list no CVE for either bug class.
- **Exploitability in this repo:** requires authenticated command access to Redis (`RESTORE` + a crafted payload). The repo's `docker-compose.yml`/`docker-compose.prod.yml` do not expose the `redis` service port to the host or public internet — it's reachable only from `backend`/`worker` containers on the compose network — which narrows practical exposure to an attacker who has already achieved code execution or SSRF-to-Redis inside the network. It does not narrow the fix priority, since the tag bump is trivial (single line, no code changes, no client-library coupling to worry about).
**Action:** bump `redis:7.4.9-alpine` → `redis:7.4.10-alpine` (or whatever alpine-tagged equivalent is published) in both `docker-compose.yml` and `docker-compose.prod.yml`.

### #511 — Atomic `submit()` / commit-then-enqueue seam

One new adjacent reference worth noting, not a fit: DBOS's Python "Transactional Outbox" docs show durable-workflow-based outbox examples, but they require adopting DBOS's own Postgres-backed workflow engine rather than layering onto the repo's existing RQ workers — not directly applicable without a much larger architecture change. No RQ-specific or generic-Redis outbox library has emerged. Recommendation unchanged: hand-roll the seam (commit in one transaction, enqueue via an on-commit hook), consistent with the pattern already discussed in `rq/rq#327`.

### #334 — PostgreSQL 18 evaluation
Two 2026 migration-mechanics guides found (Data Egret's "Ultimate Guide to Upgrading PostgreSQL 17→18," 2026-03-19; pghealth.io's tuning checklist, 2026-01-14) — both database-ops-focused (pg_dump/restore, pg_upgrade link mode, PgBouncer switchover, post-upgrade tuning). Neither covers FastAPI + SQLModel + Alembic + psycopg2 driver-level compatibility specifically — that gap still needs to be filled by the FEAT-114 draft spec itself. Notable detail for that spec: PG18 now preserves optimizer statistics across `pg_upgrade`, removing the old requirement to re-run `ANALYZE` immediately after upgrade.
