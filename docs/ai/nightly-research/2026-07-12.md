## Security Risks

### OPEN (5th cycle) — Starlette version floor below CVE-2026-48710 fix; now confirmed not to hit the secondary risk class
`backend/requirements.txt` still pins `starlette>=0.49.1`, unbounded, no lockfile. Fixed version remains 1.3.1 (Starlette 1.0.1, released 2026-05-21, is the minimum patched release). **New this cycle:** the CVE now has substantially wider public visibility — a dedicated tracking site (badhost.org), a public GitHub detection/exploit scanner (`Bhanunamikaze/BadHost-CVE-2026-48710-Exploit`), and a CCB Belgium national-CERT advisory, in addition to the CSO Online/Hacker News coverage already known from prior cycles. **Also new and verified this cycle:** several writeups flag that patching Starlette alone isn't sufficient if application code uses `request.url.path` (rebuilt from the Host header) in place of `request.scope["path"]` for auth/authorization decisions — that pattern stays exploitable regardless of framework version. I grepped this backend (`grep -rn "request.url"` / `"base_url"` / `"redirect_uri"` across `app/`) and confirmed: the only two `request.url.path` reads are in the correlation-ID logging middleware (`app/main.py:71,83`, non-security), and both OAuth `redirect_uri` values are built from the configured `settings.frontend_url` (`app/api/auth.py:205,243`), never from request Host/URL data. **This repo is not exposed to the secondary risk** — the outstanding fix genuinely is the one-line dependency floor bump, unapplied for five consecutive cycles.
**Action:** change `starlette>=0.49.1` to `starlette>=1.0.1` (or `>=1.3.1` to track current) in `backend/requirements.txt`. One line, no behavior change, no other code changes needed in this repo.

### STANDING — React 19.2.6 (repo's pinned version) has a known Server Actions/FormData regression, fixed in 19.2.7
Unchanged from last cycle: React/React-DOM 19.2.7 fixes a FormData-handling regression in Server Actions introduced in 19.2.6, the exact version this repo has pinned (`frontend/package.json`). Not a CVE, but directly actionable — any form submitted through a Server Action (auth, strategy save, profile settings) could be hitting this. Second cycle recommending the bump.

### RESOLVED / CONFIRMED SAFE — Redis and PostgreSQL server CVEs
`redis:7.4.9-alpine` (Docker) remains the fixed release for the 2026-05 CVE batch (CVE-2026-23479/23631 et al.) — no new Redis server CVEs since 2026-07-08. `postgres:16-alpine` (Docker, floating tag) continues to resolve to a patched 16.14+ build covering CVE-2026-2005 (pgcrypto heap overflow) — no new PostgreSQL CVEs found this cycle. Both unchanged from last cycle; same reproducibility caveat (stale cached image layers pre-dating the patch date would still be vulnerable).

### STANDING GUARDRAIL — redis-py 8.x / RQ version coupling
redis-py 8.x (RESP3-by-default, a breaking change) requires RQ >=2.9.1 for compatibility. Repo's current pins (`redis==7.1.1`, `rq==2.7.0`) are mutually compatible today and unaffected — but RQ is now at 2.10.0 (adds official Valkey support and an `rqworker-pool` command), widening the gap. Unchanged guardrail: **do not bump `redis` past 7.x without bumping `rq` to >=2.9.1 in the same change.**

### MONITOR — No other new CVEs this cycle
FastAPI, SQLModel, Alembic, psycopg2-binary, rq-scheduler, Next.js, TypeScript, Tailwind CSS, @xyflow/react, uvicorn: no new security advisories found since 2026-07-08 against any current or latest-available version.

### #510 — Pydantic → Zod codegen seam
**Nothing materially new.** `pydantic2zod` remains stagnant (no active development beyond dependency bumps). The actively-maintained fork **`@dmitryrechkin/json-schema-to-zod`** remains the right candidate over the now-unmaintained `json-schema-to-zod`. This cycle's search reinforced that the cross-field-validator gap (take-profit-ladder ascending-order + ≤100%-total checks) is still handled by hand-written `.refine()`/`@field_validator` pairs on each side in every surveyed approach — no tool auto-generates a cross-field check from one source of truth. `dhi` (justrach/dhi) remains a footnote: still requires writing the schema twice (Python + TS), no single-source codegen.

### #511 — Atomic `submit()` / commit-then-enqueue seam
**Nothing new.** No RQ-native (non-Django) commit-then-enqueue recipe surfaced this cycle. General 2026 background-job writeups continue to converge on the same answer already adopted as this issue's standing recommendation: a transactional-outbox table (write the job row in the same DB transaction, a separate step/worker relays it to Redis) when the enqueue must not be lost to a crash between commit and `enqueue()`. django-rq's `COMMIT_MODE='on_db_commit'` remains the closest packaged reference; no raw-RQ + SQLModel equivalent exists as a library. Recommendation unchanged: replicate the "commit the run row, enqueue after, leave a retryable row if enqueue throws" semantic manually.

### #334 — PostgreSQL 18 evaluation
**Nothing new** beyond the version/CVE state already covered above.
