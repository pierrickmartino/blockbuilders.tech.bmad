## Security Risks

### P1, NEW — Redis server: second security fix (7.4.10) not covered by the repo's pin, no CVE ID assigned yet
Redis shipped `6.2.23`, `7.2.15`, and **`7.4.10`** on **2026-07-23** (three days after the May round's `7.4.9` fix), marked `Update urgency: SECURITY` in its own release notes, fixing a **Streams shared-NACK use-after-free**: a crafted stream `RESTORE` payload can make two consumers reference the same pending-entry record; removing both frees that memory twice, giving an authenticated client a heap-corruption → potential RCE primitive. Redis's own notes assign no CVE number; some third-party write-ups label it `CVE-2026-25589` (CVSS 9.8, unofficial/unconfirmed). **The repo's exact Docker pin, `redis:7.4.9-alpine`, predates this fix and is therefore vulnerable** — the 07-27 report's "confirmed safe" verdict only accounted for the earlier May-round CVEs (CVE-2026-23479, CVE-2026-25243, CVE-2026-23631), which remain correctly fixed in 7.4.9; it did not know about this second, later flaw.
**Verified independently:** Redis's GitHub release page, two independent press write-ups, and direct confirmation that Docker Hub publishes a `redis:7.4.10-alpine` tag today.
**Action:** bump the Redis Docker image pin from `redis:7.4.9-alpine` to `redis:7.4.10-alpine` (or later) in `docker-compose.yml`. Authenticated-RCE-class, patch-only, no application code changes required.
