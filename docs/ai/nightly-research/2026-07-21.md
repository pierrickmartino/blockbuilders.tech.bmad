Since this codebase has zero `"use server"` usage, that specific regression cannot be hit here — the recommendation should be downgraded from "verify auth/save forms aren't affected" to routine hygiene. Separately, **React 19.2.8 released today** (2026-07-21, confirmed via GitHub release notes): one change, "Performance improvements when decoding" in React Server Components (`facebook/react#37087`), non-security.

**Zero non-docs commits since the last cycle**, all 10 tracked issues remain open at **zero comments each** (re-verified via `gh issue view --json comments`), and the `bot/nightly-research-*` PR backlog is still flat at **16 open, unmerged PRs** (back to #520, 2026-06-03) — fifth cycle flagging this unchanged.

## Security Risks

### RESOLVED (patch now available) — Next.js scheduled security release shipped: 16.2.11 / 15.5.21, 4 high + 5 moderate
Confirmed via two independent sources: `npm view next dist-tags` shows `latest: 16.2.11` and `backport: 15.5.21`, both new today; and the GitHub release notes for `v16.2.11` are **security-only** content listing 9 advisories:
- **High:** DoS in App Router using Server Actions · Middleware/Proxy bypass in App Router apps using Turbopack + single locale · SSRF in rewrites via attacker-controlled destination hostname · SSRF in Server Actions on custom servers
- **Moderate:** two cache-confusion advisories (requests with bodies; invalid UTF-8 byte sequences) · DoS in the Image Optimization API using SVGs · unauthenticated disclosure of internal Server Function endpoints · unbounded Server Action payload in Edge runtime

CVE IDs and individual GHSA pages are not yet queryable via the GitHub Advisory GraphQL API (indexing lag — only the pre-existing May-2026 batch, already fixed in this repo's 16.2.6 pin, returns today). Treat the version numbers above as the actionable fact; CVE IDs will backfill in the next cycle or two.

**Repo exposure, checked directly against this codebase:**
- No `middleware.ts` / `middleware.js` anywhere in `frontend/` → Turbopack/locale bypass not applicable.
- `frontend/next.config.ts` has no `rewrites()` and no custom `images` config → rewrites-SSRF and SVG Image-Optimization-DoS not applicable.
- No custom server file (`server.js`/`server.ts`) → SSRF-via-Server-Actions-on-custom-servers not applicable.
- No WebSocket usage found in `frontend/src`.
- **No `"use server"` directive anywhere in `frontend/src`** — this app does not use Next.js Server Actions; forms call the FastAPI backend directly. This also rules out the unbounded-Server-Action-payload advisory.
- The two remaining advisories (DoS in App Router using Server Actions; unauthenticated disclosure of internal Server Function endpoints) live in Next.js's own request-handling internals and could theoretically be reachable regardless of whether the app code uses Server Actions itself — no way to fully rule these out without the eventual CVE technical writeup.

**Action:** bump `"next": "16.2.6"` → `"16.2.11"` in `frontend/package.json`. This is a patch-only release (no breaking changes expected in a security point release); standard `npm install && npm run build && npm run lint` should be sufficient verification.

### STANDING, reframed this cycle — React 19.2.6 Server Actions/FormData regression: confirmed not reachable in this codebase
Re-verified: grepped all of `frontend/src` for `"use server"` — zero matches. This app doesn't use Next.js Server Actions (auth, strategy save, and profile settings all go through client-side calls to the FastAPI backend, per `frontend/CLAUDE.md`'s stack description and confirmed by the absence of any `action={...}` server-action wiring). The FormData regression fixed in 19.2.7 therefore cannot be triggered here. **Downgrade this from "verify forms" to routine patch hygiene** — still worth bumping to pick up the fix and stay current, but no forms need re-testing for this specific issue.
**New today:** React 19.2.8 released 2026-07-21 — GitHub release notes confirm a single change, "Performance improvements when decoding" in React Server Components (PR #37087), non-security, no functional risk noted.

### OPEN, unchanged — Starlette version floor below CVE-2026-48710 ("BadHost") fix, but likely not live-exploitable in fresh builds
No change from the 2026-07-20 assessment: `starlette>=0.49.1` (unbounded, no lockfile) resolves to the latest available Starlette (currently 1.3.1, patched) on any fresh `pip install`, since `fastapi==0.136.1`'s own floor (`starlette>=0.46.0`) doesn't cap it lower either. ### #511 — Atomic `submit()` / commit-then-enqueue seam
**Nothing new this cycle.** Re-searched transactional-outbox patterns against Redis specifically: Redis Streams-based outbox implementations exist as a *pattern* (state and outbox both in Redis, single atomic write), but none package the RQ + SQLModel + Postgres combination this repo uses — the pattern would need hand-adaptation either way. Standing recommendation unchanged: a transactional-outbox table (write the job row in the same DB transaction, a separate relay step pushes to Redis) remains the right-sized fix; `django-rq`'s `COMMIT_MODE='on_db_commit'` remains the closest packaged reference for the "commit-then-enqueue" semantic.
