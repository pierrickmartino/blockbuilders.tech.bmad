## Executive Summary

**Starlette released three new versions today (1.5.0, 1.5.1, 1.6.0, all 2026-08-08), none of which close the repo's existing floor-pin security gap.** `1.5.0`/`1.5.1` harden `GZipMiddleware`/`FileResponse` (streamed-chunk flushing, rejecting inverted single-byte Range headers, capping `FileResponse` to 100 ranges); `1.6.0` adds a `max_body_size` option. None carry a CVE. I independently re-verified the full CVE list against OSV.dev rather than trusting prior-cycle text: the repo's `starlette>=0.49.1` floor is below the fix version for **5 distinct CVEs (2 HIGH, 2 MODERATE, 1 LOW)** — `CVE-2026-48818` (HIGH, SSRF/NTLM credential theft via UNC paths, fixed `1.1.0`), `CVE-2026-54283` (HIGH, `request.form()` limits silently ignored, fixed `1.3.1`), `CVE-2026-48710` (MODERATE, "BadHost" header-poisoning bypass, fixed `1.0.1`), `CVE-2026-48817` (MODERATE, arbitrary HTTP method dispatch, fixed `1.1.0`), `CVE-2026-54282` (LOW, unvalidated path in authority poisoning, fixed `1.3.0`). ### P2, updated — Starlette: three new releases today (1.5.0, 1.5.1, 1.6.0), non-security but widens the floor-pin gap; full CVE list independently re-verified against OSV.dev
Starlette shipped **1.5.0** (07:19 UTC), **1.5.1** (17:00 UTC), and **1.6.0** (18:27 UTC), all on 2026-08-08. None carry CVE references:
- `1.5.0`: `GZipMiddleware` improvements — `exclude_content_types` param, flush-per-streamed-chunk, skip compression of partial responses.
- `1.5.1`: reject inverted single-byte `Range` headers (`bytes=5-4`) and cap `FileResponse` to 100 ranges — a hardening fix for a resource-exhaustion-adjacent edge case, not assigned a CVE.
- `1.6.0`: adds `max_body_size` to `Starlette` and route classes; exposes `http.response.debug` info via response extensions.

**Full CVE re-verification (queried OSV.dev directly today, not carried forward from prior-cycle text):** the repo's `starlette>=0.49.1` floor sits below the fix version for 5 distinct CVEs:

| Severity | CVE | Summary | Fixed in |
|---|---|---|---|
| HIGH | CVE-2026-48818 | SSRF + NTLM credential theft via UNC paths in `StaticFiles` (Windows) | `1.1.0` |
| HIGH | CVE-2026-54283 | `request.form()` limits silently ignored for `application/x-www-form-urlencoded` | `1.3.1` |
| MODERATE | CVE-2026-48710 | "BadHost" — missing `Host` header validation poisons `request.url.path`, bypassing path-based security checks | `1.0.1` |
| MODERATE | CVE-2026-48817 | Arbitrary HTTP method dispatched to `HTTPEndpoint` attributes | `1.1.0` |
| LOW | CVE-2026-54282 | Unvalidated request path concatenated into authority poisons `request.url` | `1.3.0` |

This confirms the "5 CVEs, 2 HIGH" figure repeated across prior cycles is accurate, now checked against the primary source rather than carried forward as text.
**Action unchanged:** change `starlette>=0.49.1` to `starlette>=1.3.1` (closes all 5) in `backend/requirements.txt`. `fastapi==0.141.1` (latest, unchanged, released 2026-07-29) still only requires `starlette>=0.46.0` — FastAPI's own floor does not protect against these CVEs. Given today's three releases landed within hours of each other, bundling the floor-pin bump with a routine version update to `1.6.0` is reasonable.
