## Security Risks

### NEW, P1, CONFIRMED — Redis Streams `RESTORE` use-after-free → RCE; repo's exact pinned tag (7.4.9) is vulnerable, fixed in 7.4.10
Redis published an out-of-band security release on **2026-07-23**: 7.4.10 (also 7.2.15, 6.2.23, and 8.2.8/8.4.5/8.6.5/8.8.1 for the newer branches). The bug: a crafted stream `RESTORE` payload can make two consumers share the same NACK (pending-entry record); when both are removed, the same object is freed twice, and the published exploit escalates this use-after-free into arbitrary memory access and ultimately code execution. Security researchers published a working authenticated RCE proof-of-concept against stock Redis versions including **7.4.9** on 2026-07-23/24. Redis's own release notes do not list a CVE/CVSS for this specific bug class as of writing, but coverage treats it as critical, and it is described as a follow-on to the previously-tracked CVE-2026-25589 family (the May 2026 patch level — which includes 7.4.9 — did not include the shared-NACK ownership guard that closes this hole).
**Repo exposure:** `docker-compose.yml` publishes Redis to the host (`ports: "6379:6379"`) — reachable from outside the Compose network in dev. `docker-compose.prod.yml` does **not** publish a Redis port — reachable only from other containers on the Compose network in prod, a narrower but non-zero blast radius (any compromised container, or a misconfigured firewall, still reaches it). A grep of `backend/app/` found no direct Streams command usage (RQ doesn't use Streams internally), which rules out this repo's *own code* as an attack vector but does not rule out an attacker who can reach the Redis port directly and issue `RESTORE` themselves.
**Action:** bump `redis:7.4.9-alpine` → `redis:7.4.10-alpine` (or later) in both `docker-compose.yml` and `docker-compose.prod.yml`. This is a same-major patch bump; no RQ/redis-py compatibility concerns apply (server-side only).
