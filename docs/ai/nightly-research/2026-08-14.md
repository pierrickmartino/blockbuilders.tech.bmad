## Security Risks

### NEW, P0 — PostgreSQL: 28 CVEs fixed in 18.6/17.11/**16.15**/15.19/14.24 (released 2026-08-13); repo's `postgres:16-alpine` floating tag has not been re-pulled
The PostgreSQL Global Development Group released a coordinated security batch on **2026-08-13** fixing 28 CVEs across all supported major versions, alongside PostgreSQL 19 Beta 3. Repo runs `postgres:16-alpine` (a **floating** Docker tag — unlike Redis's exact-pin, this tag auto-resolves to the newest 16.x point release on pull, and `16.15-alpine` is already published on Docker Hub). No `docker-compose.yml` edit is required, but the running/previously-pulled image **will not update itself** — a deliberate `docker pull` + service recreate (dev and prod) is needed to actually receive the fix.

The most severe CVEs affecting the 16.x line (CVSS 8.8 unless noted, all confirmed via postgresql.org's own security advisory page and cross-referenced against the release announcement):

**Applicability caveat (needs a follow-up check, not assumed):** several of the highest-severity CVEs are in contrib modules or PL languages (`plperl`, `pltcl`, `fuzzystrmatch`, `pg_stat_statements`) that this repo may or may not have enabled — a quick audit of `CREATE EXTENSION` usage in the Alembic migration history would confirm actual exposure before treating every CVE in the table as directly exploitable. The `pg_dump`/`psql` client-side CVEs (CVE-2026-19385, CVE-2026-18408) apply regardless of extension usage, since backup/restore tooling is universal.
**Action:** pull `postgres:16-alpine` (resolves to 16.15) and recreate the `db` service in both dev and prod compose stacks; confirm via `SELECT version();` post-deploy. Separately, audit enabled extensions to scope which contrib-module CVEs actually apply.
