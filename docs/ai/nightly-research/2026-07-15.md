## Security Risks

### OPEN (6th cycle) — Starlette version floor below CVE-2026-48710 fix
`backend/requirements.txt` still pins `starlette>=0.49.1`, unbounded, no lockfile. Fixed version remains 1.3.1 (Starlette 1.0.1, released 2026-05-21, is the minimum patched release). No new developments found this cycle — all retrieved sources (badhost.org, GitHub exploit scanner, CCB Belgium advisory, CSO Online, Hacker News, InfoQ, the FastAPI discussion thread) predate 2026-07-08 and were already cited in the prior report. No confirmed in-the-wild exploitation reports have surfaced in any cycle to date. As established in the 2026-07-12 cycle, this repo's own code is not exposed to the secondary `request.url.path`-based risk class (the only two usages are in non-security logging middleware; OAuth `redirect_uri` is built from configured `settings.frontend_url`, never request Host data) — the outstanding fix genuinely is the one-line dependency floor bump.
**Action:** change `starlette>=0.49.1` to `starlette>=1.0.1` (or `>=1.3.1` to track current) in `backend/requirements.txt`. One line, no behavior change, no other code changes needed in this repo.

### STANDING — React 19.2.6 (repo's pinned version) has a known Server Actions/FormData regression, fixed in 19.2.7
Unchanged from last cycle: React/React-DOM 19.2.7 (released 2026-06-01) fixed a FormData-handling regression in Server Actions introduced in 19.2.6, the exact version this repo has pinned (`frontend/package.json`). Not a CVE, but directly actionable — any form submitted through a Server Action (auth, strategy save, profile settings) could be hitting this. Third cycle recommending the bump.

### RESEARCH GAP (new) — Docker image CVE scans could not be refreshed via web search
`redis:7.4.9-alpine` and `postgres:16-alpine` (floating tag) were previously assessed as resolving to patched builds, but this cycle's web-search-based approach could not produce a version-specific scan result for either tag — results kept surfacing older Alpine-tag advisories not applicable to the pinned versions. This is a tooling limitation of the research method (web search), not new evidence of risk. **Recommend running an actual `trivy image` or `docker scout cves` scan** against the pulled images in this repo as a more reliable check than continuing to rely on web search for Docker base-image CVE status in future cycles.

### STANDING GUARDRAIL — redis-py 8.x / RQ version coupling
redis-py 8.x (RESP3-by-default, a breaking change, with `protocol=2`/`legacy_responses=False` escape hatches) requires RQ >=2.9.1 for compatibility. Repo's current pins (`redis==7.1.1`, `rq==2.7.0`) are mutually compatible today and unaffected — RQ is now at 2.10.0 (2026-06-20), widening the gap further. Unchanged guardrail: **do not bump `redis` past 7.x without bumping `rq` to >=2.9.1 in the same change.**

### MONITOR — No other new CVEs this cycle
FastAPI, SQLModel, Alembic, psycopg2-binary, rq-scheduler, Next.js, TypeScript, Tailwind CSS, @xyflow/react, uvicorn, stripe, bcrypt, joserfc, httpx: no new security advisories found since 2026-07-08 against any current or latest-available version. ### #510 — Pydantic → Zod codegen seam
**Nothing materially new.** `pydantic2zod` (argyle-engineering) remains stagnant with no update addressing cross-field validators. The actively-maintained fork **`@dmitryrechkin/json-schema-to-zod`** remains the right candidate over the unmaintained upstream `json-schema-to-zod`. `dhi` (justrach/dhi) picked up a minor version bump (1.3.1, "Zig + SIMD WASM," claims 520x faster than Pydantic) but this is a **validation-engine replacement, not a codegen bridge** — still requires hand-writing the schema twice (Python + TS), still no cross-field-validator generation. No tool found anywhere auto-generates a cross-field check (e.g., take-profit ladder ascending-order + ≤100%-total) from one source of truth.

### #511 — Atomic `submit()` / commit-then-enqueue seam
**Nothing new.** No RQ-native (non-Django) commit-then-enqueue recipe surfaced this cycle. General 2026 background-job writeups continue to converge on the same answer already adopted as this issue's standing recommendation: a transactional-outbox table (write the job row in the same DB transaction, a separate step/worker relays it to Redis) when the enqueue must not be lost to a crash between commit and `enqueue()`. django-rq's `COMMIT_MODE='on_db_commit'` remains the closest packaged reference; no raw-RQ + SQLModel equivalent exists as a library. One new comparison point this cycle: BullMQ (Node ecosystem, not RQ) writeups confirm the identical commit-then-enqueue race is a known cross-ecosystem problem with the same outbox fix — reinforces rather than changes the standing recommendation. Recommendation unchanged: replicate the "commit the run row, enqueue after, leave a retryable row if enqueue throws" semantic manually.

### #334 — PostgreSQL 18 evaluation
**Nothing new** beyond the version/CVE state already covered above. PostgreSQL 19 Beta 1's headline features (2x faster FK-check inserts, anti-join optimizations, incremental sort, SQL/PGQ) are informational context for a future plan, not evaluation-changing — no OLAP/backtest-numeric-workload-specific benchmark data exists yet for either 18.x or 19.
